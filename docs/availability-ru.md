# Доступ из России без VPN

## Что установлено

На 14 ноября 2026 года интерфейс опубликован на `https://vosavasof.github.io/Yasno/`, а запросы кабинетов идут на отдельный домен действующего API, указанный в конфигурации опубликованного сайта. Серверная часть размещена через Cloudflare Workers. Если без VPN появляется интерфейс с ошибкой подключения, HTML и JavaScript GitHub Pages уже загрузились; проверять прежде всего нужно соединение с API. По одному сообщению нельзя отличить ограничения сети от DNS, TLS, тайм-аута или сбоя сервера.

Проверка со стороны разработчика из другой страны не подтверждает доступность у российского провайдера. Нужны проверки без VPN с домашнего интернета и мобильной сети в РФ: открыть сайт, войти, получить расписание, сделать запись и проверить тестовую оплату. Не нужно публиковать семейные ссылки, пароли, ключи ЮKassa или содержимое клиентской базы для диагностики.

Cloudflare официально сообщает о нарушениях доступности для российских пользователей: https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/. Это подтверждает возможность такого ограничения, но не устанавливает точную причину конкретного подключения.

## Что меняют настройки GitHub

- Переменная репозитория `YASNA_API_BASE` позволяет заменить **адрес сервера**, используемый браузером. Она не перемещает код и базу. Новый API должен быть развёрнут, содержать перенесённые данные и разрешать авторизованные запросы с адреса интерфейса. Не используйте адреса публичных прокси: через API проходят данные семей и подтверждения оплат.
- Переменная `PAGES_BASE_PATH` задаёт путь интерфейса, по умолчанию `/Yasno/`. На собственном домене в корне нужен `/`. Адрес `PUBLIC_APP_URL` серверной версии также должен соответствовать реальному адресу кабинета.
- Переменные находятся в **Settings → Secrets and variables → Actions → Variables**. После изменения повторно запустите workflow «Публикация сайта». Пустые значения сохраняют существующие настройки. Адрес API публичен; секретный ключ ЮKassa сюда не добавляется.
- `Settings → Pages → Custom domain` меняет имя сайта, но оставляет размещение на GitHub Pages. Собственный домен API поверх Cloudflare также не устраняет зависимость от этой сети. Поэтому одна смена домена не гарантирует результат.
- `Enforce HTTPS`, изменение CORS и увеличение числа повторных запросов не устраняют блокировку или деградацию маршрута до сервера. Открывать CORS для всех адресов или отключать HTTPS не требуется.

Раньше build-скрипт читал `YASNA_API_BASE`, но workflow не передавал repository variables в окружение сборки. Эта ошибка исправлена. При пустой переменной повторная сборка читает адрес из действующей публичной конфигурации; сама правка не решает доступ из РФ.

## Рекомендуемое размещение

Один домен и один VPS в российском дата-центре:

```text
Телефон родителя → HTTPS на собственном домене → приложение Node.js
                                                 ├─ /api/…
                                                 ├─ SQLite и файлы чеков
                                                 └─ ЮKassa (оплаты)
```

На таком размещении `dist/config.js` уже использует `YASNA_API_BASE=''`: API запрашивается с того же домена, отдельный домен прежнего API браузеру не нужен. GitHub остаётся хранилищем кода и средством доставки обновлений, а родители при обычной работе к нему не обращаются. Шрифты, логотипы и модуль чтения Excel уже загружаются с самого сайта. Внешняя форма ЮKassa подключается только при открытии оплаты.

Для небольшой мастерской можно начать с 1 vCPU, 1–2 ГБ памяти и постоянного диска с резервным копированием. Нужны Linux, Docker/Compose, домен с A-записью на сервер и открытые 80/443. Подходят российские VPS, например у Timeweb Cloud, Beget или Selectel; выбирайте именно российскую локацию и проверяйте тариф у провайдера. Обычный тариф только с PHP без Node.js/Docker не подойдёт. У выбранной площадки также нужно проверить доступ к API ЮKassa.

Не ставьте Cloudflare Proxy перед новым сайтом при первичной проверке доступности. Для начала достаточно DNS провайдера/регистратора, прямого адреса VPS и HTTPS через Caddy. Стабильность всё равно проверяется в сетях родителей: гарантировать доступность у всех операторов одной настройкой нельзя.

## Порядок переноса

1. Подготовить VPS и домен, запустить `compose.yaml` по инструкции в README. Пока их нет, переносить работающую базу некуда.
2. Сохранить резервную копию действующих клиентов, родителей, расписания, посещений, оплат, остатков и содержимого чеков. Перед переключением согласовать окно переноса без новых записей и оплат.
3. Отдельно сверить незавершённые заказы ЮKassa. JSON-копия журнала не содержит реестра онлайн-заказов и зашифрованных настроек магазина. Для сохранения истории тестовых/незавершённых заказов нужен отдельный защищённый перенос этих серверных таблиц; обычного JSON-восстановления недостаточно. Ключи доступа и секреты не размещаются в GitHub.
4. Восстановить данные на новом сервере, проверить суммы, остатки и чеки. Доступ мастера создать на новом сервере, родителям выдать новые ссылки. Настройки ЮKassa ввести заново через кабинет мастера; не копировать зашифрованный ключ из другой базы без его ключа шифрования.
5. Указать новый webhook URL в ЮKassa, проверить тестовую оплату и автоматическое отражение её статуса. Ссылки возврата новых платежей должны вести на новый домен. Старые заказы сверять до закрытия прежнего сервера.
6. Проверить работу без VPN с домашнего интернета и мобильной сети в РФ. После успешной проверки переключить родителей на новый адрес. Прежнюю базу и резервную копию сохранить до завершения сверки.

Это план переноса, а не выполненное развёртывание. Сервер, домен, DNS и действующие данные текущего приложения этой правкой не изменяются.
